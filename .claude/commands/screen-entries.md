# /screen-entries — 書類選考評価コマンド

採用担当が手動で実行するコマンド。選考ステップが「エントリー」になっている応募者を対象に、
書類（履歴書・職務経歴書）と求人要件を照合してAI評価を生成し、HERP Hireの応募タイムラインに
コメントとして投稿する。

## 引数（任意）: $ARGUMENTS

- **省略時**: 通常フロー。選考ステップ「エントリー」かつ`status=active`の応募者全員を対象とする（Step 1〜4）
- **氏名 または candidacyId を指定した場合**: 選考ステップ・ステータスに関わらず、指定した応募者
  **1名のみ**を対象に処理する（「個別指定モード」）。詳細は下記「個別指定モード」の節を参照

## 個別指定モード（$ARGUMENTS が指定された場合）

Step 1（対象抽出）を以下に置き換える。Step 1.5〜Step 4は原則通常フローと同じだが、差分を明記する。

1. **対象の特定**
   - `$ARGUMENTS`がUUID形式（candidacyId）の場合: `GET /v1/candidacies/{candidacyId}` で直接取得する
   - `$ARGUMENTS`が氏名の場合: `GET /v1/candidacies`を**`status`パラメータを付けずに**ページングして
     全件取得し、氏名が一致する応募を client 側でフィルタする
     （`name`等のクエリパラメータによるサーバー側絞り込みは非対応のため使用しないこと。実データで確認済み）
     - レート制限（100 req/min）に留意し、ページ取得中は`x-remaining-request`ヘッダーを見ながら間隔調整する
     - 全件スキャンは件数が多い（数十〜100ページ規模になりうる）ため、時間がかかる旨を先に一言断ってから実行する
   - 一致が複数件（同一人物が複数職種に応募している等）の場合は、応募ごとの職種・応募日・選考ステップ・
     ステータスを一覧表示し、どれを対象とするか確認する
   - 一致が0件の場合はその旨を報告して終了する（Step 2以降には進まない）

2. **Step 1.5（処理済み除外）の扱い**
   - 通常フロー同様に既存タイムラインコメントを確認するが、個別指定モードでは`🤖 by Claude Code`
     マーカーが見つかっても自動スキップしない。「既に評価済みですが再実行しますか？」とユーザーに確認し、
     re-runの意思が確認できた場合のみStep 3へ進む
     （ユーザーが名指しで実行を依頼している時点で明示的な意図があるとみなすため）

3. **Step 2（一覧提示・実行確認）は1名のみでも省略しない**
   - 対象者の氏名・応募職種・応募日に加えて、選考ステップとステータス（通常フローと異なり
     エントリー以外・非activeの可能性があるため）も明示する

4. **Step 3以降（評価生成・投稿・結果サマリー）は通常フローと同じ手順で行う**

## 前提・環境変数
- `HERP_API_KEY` : HERP Hire APIキー（スコープ: `candidacy:read`, `candidacy:write`, `requisition:read` を含むもの。管理画面右上メニュー「APIキー」から発行）
- `HERP_API_BASE` : `https://public-api.herp.cloud/hire`
- 認証ヘッダー: `Authorization: Bearer ${HERP_API_KEY}`
- レート制限: テナントごと 100 req/min。対象者数が多い場合はレスポンスヘッダー `x-remaining-request` を見ながら間隔を調整する

## 使用エンドポイント一覧
| 用途 | メソッド・パス |
|---|---|
| 対象抽出 | `GET /v1/candidacies?step=entry&status=active` |
| 応募詳細取得 | `GET /v1/candidacies/{candidacyId}` |
| 添付ファイル一覧取得 | `GET /v1/candidacies/{candidacyId}/files` |
| ファイル実体取得 | `GET /v1/candidacies/{candidacyId}/files/{fileId}` |
| 求人要件取得 | `GET /v1/requisitions` |
| 処理済み判定用 | `GET /v1/candidacies/{candidacyId}/timeline-comments` |
| 評価投稿 | `POST /v1/candidacies/{candidacyId}/timeline-comments`（`textType: "text/markdown"`） |

※応募の`tags`フィールドは読み取りのみ可能で、更新用エンドポイントは存在しない
（2026年8月時点のAPIドキュメント確認済み）。そのため二重投稿防止はタグではなく
タイムラインコメントの既存チェックで行う。

## 評価基準ファイル
- `criteria/評価基準.xlsx`（「ランク基準」「希望人材」の2シート）を正とする
- 旧`criteria/criteria.yaml`は廃止（このファイルは参照しない）

## 処理フロー

### Step 1. 対象抽出
- `GET /v1/candidacies?step=entry&status=active` で選考ステップ「エントリー」かつ選考中の応募一覧を取得する
- `hasNextPage: true` の場合は `page` パラメータを進めて全件取得する
- 対象が0件の場合はその旨を報告して終了する

### Step 1.5. 処理済み除外
- 各応募について `GET /v1/candidacies/{candidacyId}/timeline-comments` を取得し、
  本文末尾に `🤖 by Claude Code` を含むコメントが既に存在する場合はスキップ対象とする

### Step 2. 一覧提示・実行確認（必須。省略しない）
- Step1.5適用後の対象者の氏名・応募職種・応募日を一覧表示し、ユーザーに実行してよいか確認する
- 確認が取れるまで Step 3 以降には進まない

### Step 3. 応募ごとの評価生成（対象者ごとにループ）
各応募について以下を行う。

1. **書類取得**: `GET /v1/candidacies/{candidacyId}/files` でファイル一覧（`type: "resume"` 等）を取得し、
   各`fileId`について `GET /v1/candidacies/{candidacyId}/files/{fileId}` で実体を取得
2. **評価基準取得**（①②を必ず両方取得する。フォールバックではなく併用）:
   a. **①内部ランク基準**: `criteria/評価基準.xlsx` の「ランク基準」シートを参照する。
      対象の`requisitionId`と一致する行（S/A/B/C最大4行）を取得する。
      - シート上の`requisitionId`列は**URLがそのまま貼られている場合がある**ため、
        値に`http`が含まれる場合は末尾のパスセグメント（`/id/`の後ろの文字列）を
        UUIDとして抽出してから比較すること
      - 一致する行が0件（=未記入）の場合は、①なしとして扱う
   b. **②求人要件（必須スキル等）**: `GET /v1/requisitions` から、`requisitionId`に対応する
      `requiredSkills`（必須スキル）/`preferredSkills`（歓迎スキル）/`personality`（求める人物像）を
      **①の有無に関わらず必ず取得する**
   c. **希望人材マッチング用データ**: `criteria/評価基準.xlsx` の「希望人材」シートから、
      同じ`requisitionId`（同様にURL/UUID両対応で比較）に該当する行をすべて取得する
      （1人の推薦者が同一職種に複数行書いている場合があるので、全行を保持する）
3. **評価生成（二段階モデル運用でトークン消費を抑える）**:

   候補者1人につきサブエージェント（Agentツール）を1体立てて評価文を生成する。
   その際、以下の二段階モデル運用を必ず行うこと（トークンコスト削減のための標準運用）。

   a. **一次評価（`model: "haiku"`）**: まず全候補者について、Haikuモデルのサブエージェントに
      書類・求人要件・判定ロジック（下記）を渡し、評価文を生成させる。
      その際、以下のいずれかに該当する場合のみ「要再評価」である旨を（投稿本文とは別に、
      エージェントからの報告として）明示させること。**単に判定がB（暫定）であることや、
      良い点・懸念点が両方あるという理由だけではエスカレーションしないこと**
      （内部ランク基準が未整備の職種ではBが通常の結果であり、それ自体は「要再評価」の
      根拠にならない）：
      - 書類間（履歴書・職務経歴書・推薦状・エージェント資料等）で経歴・在籍期間・学歴等に
        明確な矛盾や不整合がある
      - 必須条件を満たすかどうかの判断が資料からは確信を持てない（記載が曖昧・情報不足で
        Step Aの判定自体が困難）
      - 経歴の信憑性に疑義がある、または通常の書類選考担当なら一次判定を鵜呑みにせず
        必ず二重チェックしたくなるような、特筆すべき重大な懸念がある場合に限る
   b. **エスカレーション（`model: "sonnet"`）**: aで「要再評価」となった候補者のみ、
      同じ書類・求人要件をあらためてSonnetモデルのサブエージェントに渡し、
      一次評価の内容（判定・懸念点）を踏まえた上で独立して読み直させ、評価を確定させる。
      二次評価が出た場合はそちらを最終版として採用し、一次評価は破棄する。
   c. 「要再評価」に該当しなかった候補者は、一次評価（Haiku）の結果をそのまま最終版として採用する
   d. 複数候補者を一括処理する場合、似た職種・似た書類分量の候補者は数名まとめて1回のエージェント
      呼び出しにまとめてよい（エージェント起動ごとの固定コストを人数分で按分できるため）。
      ただし1回あたりの書類量が多くなりすぎる場合（合計で数十ページを超えるなど）は無理に
      まとめず分割すること

   **判定ロジック（②で足切り→①で詳細ランク→希望人材マッチング）**
   ```
   Step A: ②の必須スキル（requiredSkills）を満たしているか確認する
     → 明らかに満たさない場合：原則「C（見送り）」とし、①のランク基準は
       参考情報として■総評に記載するに留める
     → 満たす場合：Step Bへ進む

   Step B: ①（評価基準.xlsx「ランク基準」シート）が当該職種に存在するか確認する
     → 存在する場合：①のS/A/B/Cランク基準に沿って詳細判定する
     → 存在しない場合：②の歓迎スキル（preferredSkills）・求める人物像（personality）との
       合致度から暫定でB/Cのみ判定し、「詳細基準（①）未整備のため暫定判定」と明記する

   Step C: 「希望人材」シートの該当行（Step2c）と候補者を照合する
     → 候補者のプロフィール（年齢・経験・スキル・資格・人柄等）が、いずれかの行の
       条件と十分に合致する場合：その行の「推薦者」名を■提案するメンバーに記載する
       （複数の推薦者に合致する場合は全員記載してよい）
     → どの行にも合致しない場合：■提案するメンバーは「該当者なし」と明記する
   ```

   ```
   【書類選考 判定: S/A/B/C】〇〇推奨
   学歴: 〇〇（偏差値等の付記可能な場合は付記）
   属性情報（年齢／応募経路）
   ※判定材料: ①内部ランク基準（あり/暫定判定）／②必須・歓迎スキル

   ■ 良い点
   - ...

   ■ 懸念点
   - ...

   ■ 確認ポイント
   - ...

   ■ 提案するメンバー
   - （希望人材シートと合致した推薦者名。合致しなければ「該当者なし」）

   ■ 総評（判定が割れる場合や、別の物差しでは評価が変わる場合に記載）
   - ...
   ```

   - 判定ランク: **S（絶対ほしい）／A（ほしい）／B（会ってみたい）／C（お見送り）** の4段階
   - ②の必須スキル未充足による「C」判定と、①のランク基準による「C」判定は、
     ■総評でどちらの理由によるものか明記する
   - 判定が厳しく出る場合でも、別の評価軸なら通る可能性があれば「■ 総評」で必ず言及する
   - **候補者本人の希望年収・現年収に関する情報、および年収を理由とした評価コメントは、
     タイムラインへの投稿本文に一切含めないこと**（属性情報・良い点・懸念点・確認ポイント・
     総評のいずれにも記載しない）。求人の年収レンジ自体も本文には記載しない。
     年収面で気になる点があっても、選考ステップ上の別の手段（社内Slack等）で
     人に直接伝えるべき情報であり、本コマンドの投稿対象外とする

5. **投稿**: `POST /v1/candidacies/{candidacyId}/timeline-comments` に
   `{ "body": "<評価文>", "textType": "text/markdown" }` を送信する（本文は20,000文字以内）。
   本文末尾に生成元を明示する一行を必ず付与する。
   ```
   🤖 by Claude Code
   ```
   これがStep1.5の重複チェックの目印にもなる。
6. **後処理**: 特になし（タグ更新APIが存在しないため、次回実行時はStep1.5のコメント存在チェックのみで処理済み判定を行う）

### Step 4. 結果サマリー
全件処理後、以下の形式で結果を報告する。

```
処理件数: n件
判定内訳: S n件 / A n件 / B n件 / C n件（うち必須スキル未充足によるC: n件）
モデル運用: 一次判定（Haiku）で確定 n件 / Sonnetに再評価 n件
スキップ: n件（処理済み）
エラー: n件（内容と対象者名を明記）
```

## エラーハンドリング
- ファイル取得に失敗した応募はスキップし、エラーリストに含めて後で報告する
- API呼び出しが429（レート制限）を返した場合は指数バックオフで再試行する
- 投稿は行うが選考ステップの自動変更は絶対に行わない（人の最終判断に委ねる）
