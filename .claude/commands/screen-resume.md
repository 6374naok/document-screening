# /screen-resume — 書類選考 自動一次スクリーニングコマンド

選考ステップが「書類選考」になっている応募者を対象に、社内NG基準・応募求人の必須/歓迎スキル充足度・
他求人への適性を判定し、HERP Hireの応募タイムラインにコメントとして投稿する。
**毎日AM4:00の無人自動実行を前提とするコマンド**であり、`/screen-entries`（エントリー段階の手動実行）とは
対象ステップ・判定ロジック・運用タイミングが異なる。

## 引数（任意）: $ARGUMENTS
- **省略時**: 通常フロー。選考ステップ「書類選考」かつ`status=active`の応募者全員を対象とする
- **氏名 または candidacyId を指定した場合**: `/screen-entries` の個別指定モードと同様に、
  ステップ・ステータスに関わらずその1名のみを対象に処理する（動作仕様はStep 1〜4を参照しつつ
  `/screen-entries` の「個別指定モード」の節に準拠する。全件氏名検索の重さ・レート制限対応・
  複数ヒット時の確認・処理済みマーカーの再実行確認は `/screen-entries` と同じ扱いとする）

## 絶対に守ること
- **投稿はタイムラインへのコメントのみ**。選考ステップの自動変更・タグ更新は絶対に行わない。最終判断は人が行う
- **年齢・外国籍・傷病/休職歴の3項目は自動判定しない**（社内基準スプレッドシートで`自動判定`列が`FALSE`）。
  これらを理由に「見送り」等の判定・理由文を生成することは、労働施策総合推進法・障害者雇用促進法・
  職業安定法の趣旨との関係で絶対に行わない。事実の提示のみに留める
- 深夜の無人実行のため、`/screen-entries` にある「Step2 一覧提示・実行確認」は行わない
  （実行前確認なしでStep3まで自動的に進む）

## 前提・環境変数
`/screen-entries` と同じ。`HERP_API_KEY` / `HERP_API_BASE` / レート制限（100 req/min、`x-remaining-request`
ヘッダー参照、429時は指数バックオフ）を踏襲する。

## 使用エンドポイント一覧
| 用途 | メソッド・パス |
|---|---|
| 対象抽出 | `GET /v1/candidacies?step=resumeScreening&status=active` |
| 応募詳細取得 | `GET /v1/candidacies/{candidacyId}` |
| 添付ファイル一覧取得 | `GET /v1/candidacies/{candidacyId}/files` |
| ファイル実体取得 | `GET /v1/candidacies/{candidacyId}/files/{fileId}` |
| 求人要件取得（応募求人・他求人共通） | `GET /v1/requisitions` |
| 処理済み判定用 | `GET /v1/candidacies/{candidacyId}/timeline-comments` |
| 評価投稿 | `POST /v1/candidacies/{candidacyId}/timeline-comments`（`textType: "text/markdown"`） |

## 社内基準ファイル
- **社内基準は、リポジトリにコミットされたファイルではなく、Googleスプレッドシート
  「書類選考_社内基準（自動判定用）」（fileId: `1UchqarZBWIy2YHRo1P9V1QubxSGrr69MM149Kt0l8eQ`）を
  実行のたびに直接参照する。** Googleドライブ連携（`read_file_content`等）でこのシートを取得し、
  1行1条件のテーブル（列: `カテゴリ, 自動判定, 条件, 対応, 理由文言, 備考`）をその場でパースして使う。
  このシートは小さく単一目的の専用シートのため、毎回取得しても軽量。**リポジトリには基準データを
  一切コミットしない**（社内の書類選考ロジック・人物評価基準は機密情報であり、リポジトリの公開設定に
  関わらずGitの差分・履歴に残したくないため）
- `自動判定`列が`FALSE`の行（年齢・外国籍・傷病休職歴・トランスジェンダー等）は、労働施策総合推進法・
  障害者雇用促進法・職業安定法の趣旨との関係で、**判定ロジックに使ってはならない**。事実の提示のみに使う
- Googleドライブ連携が利用できない実行環境（ローカルでの緊急実行時など）では、このシートを直接
  参照できない旨をエラーとして報告し、全員「要確認」扱いで求人要件充足度のみの判定に留める
  （社内基準なしで見送り判定を出さない。エラーハンドリング参照）
- `criteria/評価基準.xlsx`（`/screen-entries` が使う内部ランク基準・希望人材シート）は本コマンドでは使用しない

## 処理フロー

### Step 1. 対象抽出
- `GET /v1/candidacies?step=resumeScreening&status=active` で選考ステップ「書類選考」の応募一覧を取得する
- `hasNextPage: true` の場合はページングして全件取得する
- 対象が0件の場合はその旨を報告して終了する

### Step 1.5. 処理済み除外
- 各応募について `GET /v1/candidacies/{candidacyId}/timeline-comments` を取得し、
  本文末尾に `by 着信アリ🐜` を含むコメントが既に存在する場合はスキップ対象とする

### Step 2. （スキップ）
無人実行のため、事前の一覧確認・実行可否確認は行わない。Step1.5適用後の対象者に対して
そのままStep3へ進む。

### Step 3. 応募ごとの評価生成（対象者ごとにループ）

各応募について以下を行う。候補者1人につきサブエージェント（Agentツール）を1体立てて処理する
（`/screen-entries` と同じ二段階モデル運用でトークン消費を抑える。詳細は5を参照）。

1. **書類取得**: `GET /v1/candidacies/{candidacyId}/files` でファイル一覧を取得し、
   各`fileId`について `GET /v1/candidacies/{candidacyId}/files/{fileId}` で実体を取得する
2. **応募求人の要件取得**: `GET /v1/requisitions` から、`requisitionId`に対応する
   `requiredSkills`/`preferredSkills`/`personality` を取得する
3. **他求人一覧の取得（軽量）**: `GET /v1/requisitions` の全active求人について、
   求人名と`requiredSkills`の要約（1〜2行程度）だけを抜き出したコンパクトな一覧を用意する
   （後述のStep5で「見送り」時の他求人適性チェックに使う。全求人の全文を毎回渡さないこと）
4. **社内基準照合**（Googleスプレッドシート「書類選考_社内基準（自動判定用）」を直接参照。上記「社内基準ファイル」節を参照）:
   - `auto_judge: true` の項目（経験年数・現住所・職歴・働き方要望）について、書類の記載内容と
     各条件を照合する。明確に抵触する項目があれば、その項目の`理由`文言をそのまま使って
     「見送り」と判定する
   - `auto_judge: false` の項目（年齢・外国籍・傷病/休職歴）については、**判定には一切使わない**。
     書類上に記載がある事実（年齢・国籍/ビザ状況・JLPTレベル・日本就業経験年数・傷病/休職の
     記載内容など）だけを機械的に抜き出し、後述のテンプレート「■事実確認」セクションに記載する。
     記載がない項目は「記載なし」とする
   - トランスジェンダーに関する記載が書類上明確にある場合は、判定を行わずエスカレーション対象とし、
     「■確認ポイント」にSlack「書類選考キャッチアップ部屋」または「help-you稼働報告用」への
     相談を促す一文を明記する
5. **判定生成**（テンプレートは6を参照）:

   ```
   Step A: 社内基準（auto_judge: true の項目）に明確に抵触する項目があるか確認する
     → 抵触あり: 「見送り」。判定理由はその項目の理由文言をそのまま使う。求人要件充足度の
       算出は行わなくてよい（■総評で「別の求人であれば」等の言及は不要）
     → 抵触なし: Step Bへ進む

   Step B: 応募求人の必須スキル・歓迎スキルを合わせた全項目のうち、書類から充足が確認できる
     項目の割合を算出する
     → 70%以上: 「通過」
     → 70%未満: 「見送り」。Step Cへ進む

   Step C（Bで見送りとなった場合のみ）: Step3-3で用意した他求人一覧と候補者プロフィールを
     照合し、応募求人以外で適性がありそうな求人があれば■総評に記載する（求人名を挙げる程度でよい。
     詳細な再判定は不要）。該当がなければ「該当なし」と明記する

   判定に迷う場合（社内基準の抵触判断が資料からは確信を持てない、求人要件充足率の算出が
   曖昧な情報しかない等）は「要確認」とし、理由を■確認ポイントに明記する
   ```

6. **出力テンプレート**（このテンプレートに厳密に従うこと）:
   ```
   【書類選考 自動判定: 通過/見送り/要確認】
   ■ 判定理由
   - （社内基準抵触の場合はその項目の理由文言をそのまま使う／求人要件充足率の場合は
     おおよその充足率と主に不足している項目）

   ■ 良い点
   - ...

   ■ 懸念点
   - ...

   ■ 確認ポイント
   - ...（トランスジェンダーに関する記載があった場合はここにエスカレーションの一文を含める）

   ■ 事実確認（社内基準・年齢/外国籍/傷病歴）
   - 年齢: 〇〇歳（記載なしの場合はその旨）
   - 国籍/ビザ: 〇〇（記載があれば。なければ「記載なし」）
   - 傷病/休職歴: 記載なし／〇〇の記載あり
   ※これら3項目はAIの自動判定に含まれていません。判定・見送り理由の生成は行っておらず、
   事実の提示のみです。必要に応じて人が判断してください。

   ■ 他求人への適性（Step Aで見送りの場合は記載不要。Step Bで見送りの場合のみ記載）
   - 該当なし／〇〇求人であれば適性があるかもしれません

   ■ 総評
   （判定が割れうる場合や、別の観点があれば記載）

   by 着信アリ🐜
   ```
   - 本文は20,000文字以内。**候補者本人の希望年収・現年収に関する情報は一切記載しない**
     （`/screen-entries` と同じ制約。求人の年収レンジも記載しない）

7. **二段階モデル運用**（`/screen-entries` と同じ方針）:
   a. 一次評価は`model: "haiku"`のサブエージェントで行う
   b. 以下のいずれかに該当する場合のみ、同じ書類・基準を`model: "sonnet"`のサブエージェントに
      渡して独立に読み直させ、最終版として採用する。**「判定が見送りだから」「良い点・懸念点が
      両方あるから」という理由だけではエスカレーションしないこと**：
      - 書類間で経歴・在籍期間・学歴等に明確な矛盾がある
      - 社内基準への抵触有無や求人要件充足率の判断が資料からは確信を持てない
      - トランスジェンダーに関する記載など、通常の書類選考担当なら必ず二重チェックしたくなる
        特筆すべき事情がある
   c. 該当しない場合は一次評価（Haiku）の結果をそのまま採用する
   d. 似た職種・書類分量の候補者は数名まとめて1回のエージェント呼び出しにまとめてよい

### Step 4. 投稿
`POST /v1/candidacies/{candidacyId}/timeline-comments` に `{ "body": "<評価文>", "textType": "text/markdown" }`
を送信する。本文末尾の `by 着信アリ🐜` が次回実行時のStep1.5重複チェックの目印になる。

### Step 5. 結果サマリー
全件処理後、以下の形式で結果を報告する（無人実行時はこのサマリーがスケジュールタスクの実行ログ・
完了通知として残る）。

```
処理件数: n件
判定内訳: 通過 n件 / 見送り n件（うち社内基準抵触 n件・求人要件未充足 n件）/ 要確認 n件
モデル運用: 一次判定（Haiku）で確定 n件 / Sonnetに再評価 n件
事実確認のみ提示（年齢/外国籍/傷病歴に該当記載あり）: n件
スキップ: n件（処理済み）
エラー: n件（内容と対象者名を明記）
```

## エラーハンドリング
- ファイル取得に失敗した応募はスキップし、エラーリストに含めて後で報告する
- API呼び出しが429（レート制限）を返した場合は指数バックオフで再試行する
- 投稿は行うが選考ステップの自動変更は絶対に行わない（人の最終判断に委ねる）
- 社内基準スプレッドシートが読み込めない場合は、その旨をエラーとして
  報告し、全員「要確認」扱いで求人要件充足度のみの判定に留める（社内基準なしで見送り判定を出さない）
